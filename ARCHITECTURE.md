# payment-gateway — архитектура (v1)

Статус: архитектура утверждена, базовая реализация проведена в этом же
раунде (Symfony 7.4 skeleton, сущности, миграция, `PanelInterface` +
`BinancePanel`, API-контроллеры, аутентификация, поллинг-воркеры,
EasyAdmin, тесты). Документ ниже — исходная архитектура плюс два явных
отступления от неё, сделанных по прямому указанию продукт-овнера в ходе
реализации (см. "Обновления по факту реализации" сразу под этим абзацем);
остальной текст оставлен как есть для истории решений и всё ещё описывает
верно то, что не менялось.

## Обновления по факту реализации

1. **R1 (диспетчеризация входящих депозитов) решено иначе**, чем
   предполагал черновик (не "уникализация суммы"). Продукт-овнер явно
   поручил: пул заранее подготовленных адресов на панели, с холдом на
   заявку. Реализовано так:
   - Новая сущность `PanelWalletAddress` (`panel`, `currency`, `network`,
     `slotIndex`, `address`, `addressTag`, `status: free|held`,
     `heldByDepositRequestId`) — см. `src/Entity/PanelWalletAddress.php`.
   - Резерв адреса под `DepositRequest` — один атомарный `UPDATE ...
     WHERE id = (SELECT ... LIMIT 1)` в
     `PanelWalletAddressRepository::tryReserve()`, гарантирующий, что два
     параллельных запроса не возьмут один и тот же адрес (полагается на
     row-level locking MySQL/MariaDB для одного атомарного UPDATE, без
     явных транзакций/блокировок в коде приложения). Проверено интеграционным
     тестом с реальной БД (`tests/Integration/Repository/PanelWalletAddressRepositoryTest.php`).
   - Автовысвобождение адреса в пул — `WalletAddressPoolService::release()`,
     вызывается при переходе `DepositRequest` в любой терминальный статус
     (`COMPLETED`/`FAILED`/`EXPIRED`/`SUBMIT_FAILED`), включая протухание по
     `expiresAt` в `PollDepositsCommand`.
   - Размер пула конфигурируется per panel/currency/network **не** отдельным
     числом, а количеством строк `PanelWalletAddress` — админ (или команда
     `app:panel-wallets:provision --count=N`) добавляет слоты явно.
   - **Физическое ограничение Binance, как и предполагалось в риске**:
     обычный аккаунт не даёт несколько независимых адресов на одну и ту же
     пару (coin, network) — повторные вызовы `GET
     /sapi/v1/capital/deposit/address` возвращают один и тот же адрес.
     Слот 0 пула — это единственный "бесплатный" адрес с обычного аккаунта.
     Любой слот ≥1 требует настроенного суб-аккаунта Binance (email в
     `Panel.config.subAccounts["{currency}:{network}"][slotIndex-1]`,
     через который дергается `GET /sapi/v1/capital/deposit/subAddress`);
     без суб-аккаунта `BinancePanel::fetchDepositAddress()` кидает
     `PanelWalletProvisioningException` — честно, без побочных эффектов,
     а не выдаёт задвоенный адрес. Если исчерпаны все настроенные слоты —
     `WalletAddressPoolService` делает ровно одну попытку донабрать
     следующий слот "на лету" (не безграничный цикл), и если панель не
     может дать больше — заявка получает `SUBMIT_FAILED`, а не зависает.
     **Открытый организационный вопрос остаётся** (см. риск R1 ниже, он
     теперь помечен как решённый архитектурно, но не операционно): чтобы
     пул реально был "5 кошельков", нужно 5 реальных Binance-суб-аккаунтов,
     что требует включённой на бирже функции суб-аккаунтов — это вне кода.
2. **Единый статус-enum** `App\Enum\PaymentRequestStatus` — общий для
   `DepositRequest` и `WithdrawalRequest` (`NEW, AWAITING_PAYMENT,
   SUBMITTED, PROCESSING, RECEIVED, COMPLETED, FAILED, EXPIRED,
   SUBMIT_FAILED`), с единым финальным успешным статусом `COMPLETED` для
   обоих потоков — по прямому указанию продукт-овнера, см.
   `src/Enum/PaymentRequestStatus.php`.

Ниже — исходный текст архитектуры (актуален везде, кроме отмеченного выше).

Микросервис обслуживает две независимые, но структурно похожие заявки:
**заявка на пополнение** (Okean просит адрес → ждём поступления → колбек) и
**заявка на вывод** (Okean просит вывод → PG исполняет на бирже → колбек).
Обе заявки исполняются через одну из подключённых **панелей** (Binance —
первая) за общим интерфейсом.

## 1. Сущности и схема данных

### 1.1 Panel

Конфигурация конкретного провайдера (биржи/процессинга).

| Поле | Тип | Комментарий |
|---|---|---|

Обе заявки реализуют общий `PaymentRequestInterface` (не Doctrine-интерфейс, а
доменный): `getId()`, `getExternalReference()`, `getStatusForCallback():
string`, `toCallbackPayload(): array`. Это то самое "общая оркестрация сверху"
— `CallbackDispatcher` и `CallbackDelivery` работают через этот интерфейс, не
зная про Deposit/Withdrawal по отдельности.

### 1.4 Статусы и переходы

Пополнение:

```
NEW ──(запрос адреса у панели успешен)──> AWAITING_PAYMENT ──(поллинг увидел зачисление)──> RECEIVED [terminal, колбек]
 │                                              │
 │                                              └──(expiresAt прошёл, платёж не пришёл)──> EXPIRED [terminal, колбек опционален — см. §R2]
 └──(панель вернула ошибку/недоступна)──> FAILED [terminal, колбек]
```

Вывод:

```
NEW ──(вызов executeWithdrawal успешен, панель приняла)──> SUBMITTED ──(поллинг увидел подтверждение)──> COMPLETED [terminal, колбек]
 │                                                              │
 │                                                              └──(панель вернула failed/rejected)──> FAILED [terminal, колбек]
 └──(панель отклонила сразу — напр. insufficient balance)──> SUBMIT_FAILED [terminal, колбек]
```

`RECEIVED`/`COMPLETED`/`FAILED`/`EXPIRED`/`SUBMIT_FAILED` — терминальные, из
них заявка руками не возвращается (кроме явного admin override, см. §7).

### 1.5 CallbackDelivery

Отдельная сущность вместо полей "count/lastError" прямо в заявке — чтобы
хранить полную историю попыток и давать админу ручной resend без потери
предыдущих попыток.

| Поле | Тип |
|---|---|
| `id` | uuid |
| `requestType` | enum `deposit`/`withdrawal` |
| `requestId` | uuid (FK по типу) |
| `eventId` | uuid — **стабилен для одного логического события**, не меняется между попытками (см. §3.3) |
| `payload` | json — снимок тела, которое было/будет отправлено |
| `attempt` | int |
| `status` | enum `pending/sent/failed/exhausted` |
| `nextAttemptAt` | datetime, nullable |
| `lastResponseCode` | int, nullable |
| `lastError` | text, nullable |
| `createdAt` / `updatedAt` | datetime |

## 2. Абстракция панелей

```php
interface PanelInterface
{
    public function getCode(): string;

    public function createDepositAddress(DepositAddressRequest $request): DepositAddressResult;

    /**
     * @param DepositRequest[] $activeRequests заявки этой панели в AWAITING_PAYMENT
     * @return iterable<DepositStatusUpdate> только по тем заявкам, где что-то изменилось
     */
    public function checkDeposits(array $activeRequests): iterable;

    public function executeWithdrawal(WithdrawalExecutionRequest $request): WithdrawalExecutionResult;

    /**
     * @param WithdrawalRequest[] $activeRequests заявки этой панели в SUBMITTED
     * @return iterable<WithdrawalStatusUpdate>
     */
    public function checkWithdrawals(array $activeRequests): iterable;
}
```

Ключевые решения:

- **Batch-проверка, а не по одной заявке.** `checkDeposits()`/`checkWithdrawals()`
  принимают весь набор активных заявок панели и сами решают, как эффективно
  их проверить (для Binance — один вызов `GET
  /sapi/v1/capital/deposit/hisrec` / `.../withdraw/history` покрывает все
  адреса сразу). Это прямое следствие требования §4 — не давать стоимости
  поллинга расти линейно с числом заявок.
- **Интерфейс работает с DTO, не с Doctrine-сущностями напрямую.** В отличие
  от `ExchangeConnectorInterface` в rates-service (где коннектор безопасно
  читает `SourcePairMapping`, потому что это read-only тикер-поток), здесь
  операции двигают деньги. Панель не должна иметь возможность случайно
  вызвать `$entityManager->flush()` или иначе тронуть persistence — она
  только переводит вход/выход в плоские value-object'ы
  (`DepositAddressRequest`, `DepositStatusUpdate`, ...), а персистентность и
  переходы статусов — исключительно в оркестрирующем сервисе
  (`DepositRequestService`/`WithdrawalRequestService`).
- **Одна реализация на панель + общий helper-слой для HTTP/подписи**, по
  аналогии с `AbstractExchangeConnector` в rates-service: подпись запроса
  (Binance — HMAC-SHA256 query string), общая обработка `429`/`5xx` с
  backoff, маппинг кодов ошибок Binance в доменные исключения — выносится в
  `AbstractHttpPanel`, чтобы вторая панель не переизобретала это заново.
  Специфика конкретной панели (эндпоинты, формат ответа, как получить
  адрес/статус) — только в наследнике.
- **`BinancePanel implements PanelInterface`** — первая и единственная
  реализация в этом раунде проектирования.

### 2.1 Test Panel (код `binance_test`)

Обычная панель, отдельная реализация `PanelInterface`
(`src/Panel/TestPanel/TestPanel.php`). Для Okean и для всего общего кода
(`DepositRequestService`, `WithdrawalRequestService`, `WalletAddressPoolService`,
`CallbackDispatcher`, поллеры, admin) она неотличима от Binance: те же
статусы и переходы, те же события колбеков (`deposit.received`,
`deposit.expired`, `withdrawal.completed`, `withdrawal.failed`, ...), тот же
формат ответов API и payload колбека. Никаких `test_mode`/`notice`, никаких
флагов окружения. Это проверяет `tests/Functional/TestPanel/BinanceParityTest.php`
(один сценарий на реальном `BinancePanel` с замоканным HTTP и на Test Panel,
транскрипты обязаны совпасть).

Отличия ровно там, где Binance ходит во внешний API:

- **Адреса фейковые** (`TestAddressGenerator`): детерминированные от
  (валюта, сеть, номер слота), не соответствуют ни одному реальному кошельку
  (у форматов с контрольной суммой она намеренно неверна, у остальных есть
  маркер `TEST`). Слот 0..49; каждая параллельная заявка получает свой слот,
  повторный запрос с тем же `external_reference` возвращает ту же заявку и
  тот же адрес (идемпотентность в сервисе, как у Binance).
- **Поступление и исполнение вывода не определяются поллингом**:
  `checkDeposits()`/`checkWithdrawals()` пусты. Оператор двигает статусы
  вручную (`TestPanelSimulator`): кнопки «Test Panel: ...» в админке
  gateway (видны только у заявок этой панели) или
  `bin/console app:test-panel:confirm <uuid|external_reference> --status=completed [--amount=..]`
  (старое имя `app:binance-test:confirm` — алиас). Симулятор вызывает те же
  `applyStatusUpdate()`/`expire()`, что и реальные поллеры, поэтому колбек
  уходит тем же путём. Доступные переходы — те, которые могут дать поллеры
  Binance: депозит `awaiting_payment -> received|completed|expired`,
  `received -> completed` (у Binance депозит не бывает `failed`); вывод
  `submitted -> processing|completed|failed`, `processing -> completed|failed`.
- Вывод ничего не отправляет: ответ панели — `submitted` с фейковым
  референсом `TEST-WD-...`, `tx_hash` при завершении — `test-<hash>`.

Подключение — как у любой панели: строка панели в админке (`Panels`) с кодом
`binance_test`, названием «Test Panel» и галочкой `active`. Код остаётся
`binance_test`, потому что он уже прописан в `gatewayPanel` методов Okean.
`bin/console app:binance-test:install` (алиас `app:test-panel:install`)
идемпотентно создаёт/обновляет такую строку: активная, валюты и сети
копируются с панели `binance`, если она есть, иначе запасной список.
Для доставки колбеков и истечения заявок нужны обычные воркеры
(`messenger:consume async`, `app:payment-gateway:poll-deposits binance_test`).

## 3. API-контракт Okean ↔ payment-gateway

Версионированный REST JSON API, `/api/v1/...`. Аутентификация запросов
*Okean → PG* — статичный API-ключ в заголовке (`X-Api-Key`), как уже принято
в rates-service. Отдельный ключ на колбеки в обратную сторону — см. §3.3.

### 3.1 Создание заявки на пополнение

`POST /api/v1/deposits`

```json
{
  "external_reference": "okean-guest-exchange-4821",
  "currency": "USDT",
  "network": "TRC20",
  "expected_amount": "150.00"
}
```

`expected_amount` обязателен (не опционален) — он не просто для отображения,
а участвует в сопоставлении входящего платежа с заявкой, см. риск §R1.

Ответ `201 Created` (или `200 OK`, если заявка с таким `external_reference`
уже существует — см. идемпотентность ниже):

```json
{
  "id": "b3f1...",
  "external_reference": "okean-guest-exchange-4821",
  "status": "awaiting_payment",
  "currency": "USDT",
  "network": "TRC20",
  "expected_amount": "150.00",
  "address": "TXyz...",
  "address_tag": null,
  "expires_at": "2026-09-18T16:00:00Z"
}
```

Если панель не смогла выдать адрес (недоступна/ошибка) — `502 Bad Gateway` с
телом ошибки, Okean решает сам, ретраить запрос или показать пользователю
ошибку; заявка на стороне PG всё равно создаётся в статусе `failed` для
трассируемости.

**Идемпотентность:** `external_reference` уникален. Повторный `POST` с тем же
`external_reference` не создаёт вторую заявку/второй адрес — возвращает
текущее состояние существующей (`200`, не `201`). Это защищает от дублей при
ретраях на стороне Okean (таймаут, потеря ответа).

### 3.2 Создание заявки на вывод

`POST /api/v1/withdrawals`

```json
{
  "external_reference": "okean-payout-991",
  "currency": "USDT",
  "network": "TRC20",
  "amount": "148.50",
  "destination_address": "TAbc...",
  "destination_tag": null
}
```

Ответ `201`:

```json
{
  "id": "9c2e...",
  "external_reference": "okean-payout-991",
  "status": "submitted",
  "currency": "USDT",
  "network": "TRC20",
  "amount": "148.50"
}
```

Та же идемпотентность по `external_reference`, тот же смысл — повтор не
приводит к повторной отправке средств (см. `clientWithdrawalId` в §1.3).

### 3.3 Статус-эндпоинты (fallback, не основной канал)

`GET /api/v1/deposits/{id}` и `GET /api/v1/withdrawals/{id}` — на случай,
если колбек потерян и Okean хочет свериться сам. Основной канал доставки
результата — колбек, эти эндпоинты не заменяют его.

### 3.4 Колбек (webhook) PG → Okean

Отдельный статичный секрет на пару (не тот же `X-Api-Key`, которым Okean
стучится в PG — направления разные, компрометация одного не должна давать
доступ к другому).

`POST {OKEAN_CALLBACK_BASE_URL}` (URL настраивается статически в конфиге PG
на окружение, не передаётся Okean per-request — см. обоснование в §R5).

```json
{
  "event_id": "5e2a5e2a-...-uuid",
  "type": "deposit.received",
  "request_id": "b3f1...",
  "external_reference": "okean-guest-exchange-4821",
  "status": "received",
  "currency": "USDT",
  "network": "TRC20",
  "amount": "150.00",
  "occurred_at": "2026-09-18T15:42:11Z"
}
```

`type` ∈ `deposit.received`, `deposit.expired`, `deposit.failed`,
`withdrawal.completed`, `withdrawal.failed`.

Заголовки:

```
X-Timestamp: 1732000000
X-Signature: hex(hmac_sha256(secret, "{X-Timestamp}.{raw_body}"))
```

- **Подпись** — HMAC-SHA256 по `timestamp + "." + сырое тело запроса`
  (аналогично тому, как в rates-service используется статичный ключ, но тут
  это финансовые данные, поэтому подписывается тело, а не просто передаётся
  ключ в заголовке — подмена/replay тела без знания секрета невозможны).
- Okean обязан отклонять запросы с `X-Timestamp` старше ~5 минут (защита от
  replay уже перехваченного, но валидного по подписи запроса).
- **Идемпотентность через `event_id`.** `event_id` генерируется **один раз**
  при переходе в терминальный статус и **переиспользуется** во всех
  повторных попытках доставки этого же события (это не "id HTTP-попытки", а
  "id факта перехода статуса"). Okean должен дедуплицировать по `event_id`,
  не по `request_id`+`status` — так безопаснее, если в будущем появятся
  промежуточные не-терминальные колбеки.

**Retry-политика.** Доставка идёт через Symfony Messenger (см. §8) с
экспоненциальным backoff: попытки на +10с, +30с, +2мин, +10мин, +30мин,
+2ч, +6ч, далее раз в 6ч до 24ч суммарно — после чего `CallbackDelivery`
переходит в `exhausted` и заявка видна в админке как требующая ручного
вмешательства (ручной resend, см. §7). Успехом считается `2xx` от Okean;
всё остальное (включая таймаут) — повод для retry.

## 4. Поллинг депозитов

Задача: обнаружить входящий платёж на адрес, который выдала панель, без
неограниченного роста стоимости с ростом числа одновременных заявок —
прямая аналогия тому, что уже решалось в rates-service для ingestion.

**Решение:** один супервизируемый systemd-процесс на панель (по образцу
`IngestExchangeCommand` в rates-service), `app:payment-gateway:poll-deposits
<panel-code>`, с внутренним циклом (не пере-стартующий Symfony-процесс на
каждый тик — оверхед bootstrap/подключения к БД на каждый REST-вызов
неоправдан при интервале в секунды):

```
loop (каждые 15с, symfony/lock не даёт второй копии крутиться параллельно):
    activeRequests = DepositRequest::findAwaitingPaymentByPanel(panel)
    if activeRequests пуст: sleep, continue
    updates = panel.checkDeposits(activeRequests)   // 1 HTTP-вызов на панель на тик
    for each update: применить переход статуса, поставить callback-сообщение в Messenger
    expired = activeRequests с истёкшим expiresAt → EXPIRED
```

Почему стоимость не растёт неограниченно:

- **O(1) вызовов к бирже за тик**, не O(числа заявок)** — Binance отдаёт всю
  deposit-историю одним вызовом (`capital/deposit/hisrec`, с фильтром по
  `coin` и временным окном), сопоставление с конкретными заявками —
  локальная операция на стороне PG по `(address, [tag], expectedAmount)`.
  При нескольких валют/сетей одновременно — несколько вызовов за тик
  (по одному на активную комбинацию coin/network), не на заявку.
- **Заявки не поллятся вечно.** `expiresAt` (предлагается 60–180 минут,
  конфигурируемо) ограничивает набор "активных" заявок сверху — множество
  одновременно поллящихся запросов равно количеству реально ожидающих
  оплаты за последний час-два, а не всей истории.
- **Интервал 15с — компромисс,** а не жёстко зашитое число: параметр
  команды/конфига панели, можно поднять до 20–30с если нагрузка на Binance
  rate-limit станет заметной; TODO уточнить с продукт-овнером ожидаемый UX
  (сколько секунд задержки между реальной оплатой и обновлением статуса в
  Okean приемлемо) — сейчас предполагаю "как можно быстрее, но не чаще, чем
  разумно" и беру 15с как стартовое значение.

Вывод по отдельному воркеру `app:payment-gateway:poll-withdrawals
<panel-code>` — тот же паттерн, но с более длинным интервалом (60с
предлагается), т.к.:
- выводов на порядок меньше, чем депозитов (одна выплата на закрытие сделки, не активный ожидающий поток),
- задержка в обнаружении подтверждения вывода менее чувствительна к UX, чем задержка обнаружения оплаты (которая блокирует продолжение сделки в Okean),
- разделение процессов — так же, как в rates-service `IngestExchangeCommand` и `SnapshotRatesCommand` разделены — изолирует зоны отказа: падение withdrawal-поллера не останавливает обнаружение депозитов.

## 5. Вывод — исполнение и подтверждение

1. `WithdrawalRequestService` создаёт `WithdrawalRequest(status=NEW)`,
   генерирует `clientWithdrawalId` (uuid), вызывает
   `panel.executeWithdrawal()`.
2. `BinancePanel::executeWithdrawal()` дергает `POST
   /sapi/v1/capital/withdraw/apply`, **передавая `clientWithdrawalId` как
   `withdrawOrderId`** — это ключевой момент идемпотентности: если вызов
   к Binance прошёл, но ответ потерялся (таймаут на нашей стороне), повторный
   вызов с тем же `withdrawOrderId` не создаст вторую реальную выплату —
   Binance его дедуплицирует на своей стороне. Без этого поля повтор после
   сетевого сбоя рискует задвоить реальный перевод денег.
3. Статус переходит в `SUBMITTED`, сохраняется `panelWithdrawalReference`
   (id, который вернул Binance).
4. Withdrawal-поллер батчем спрашивает `GET
   /sapi/v1/capital/withdraw/history`, сопоставляет по
   `panelWithdrawalReference`/`withdrawOrderId`, обновляет статус
   (`COMPLETED`/`FAILED`) и `txHash`.
5. Колбек в Okean по тому же механизму, что и депозит (§3.4, §1.5).

## 6. Хранение секретов панелей

API-ключи Binance для вывода — не read-only, компрометация = прямая потеря
денег. Решение (envelope encryption, обоснование):

- **Мастер-ключ** (`PANEL_CREDENTIALS_KEY`) живёт только в env
  (`.env.local`/секрет-хранилище инфраструктуры), никогда не в БД и не в
  git. Если в инфраструктуре аккаунта уже есть secret-manager (Vault/SSM/…)
  — мастер-ключ должен provision-иться оттуда; если нет — это открытый
  инфраструктурный вопрос (§R6), для v1 минимально приемлем env-файл с
  ограниченными правами на хосте.
- **Сами credentials панели (api key/secret) хранятся в БД, но
  зашифрованы** этим мастер-ключом (libsodium `crypto_secretbox`,
  реализуется как Doctrine custom type/атрибут на поле `Panel::credentials`,
  расшифровка только в момент построения HTTP-клиента панели, никогда не
  логируется и не сериализуется в API/EasyAdmin-ответы).
- Почему не «только env» (одна панель = одна переменная окружения)
  напрямую: продукт хочет управлять панелями через админку и добавлять
  новые без деплоя (это явно следует из "будут несколько панелей" +
  общий admin-раздел §7) — чистый env этого не даёт. Почему не «просто
  plaintext в БД»: это реальные торговые/выводные ключи биржи, а не
  read-only рыночные данные (как в rates-service) — там БД без доп.
  шифрования была оправдана, здесь нет.
- В EasyAdmin поле credentials — write-only (при редактировании можно
  задать новое значение, при просмотре/списке никогда не показывается,
  даже замаскированным — по тому же принципу, что и поле пароля).

## 7. Admin-панель (EasyAdmin)

- **PanelCrudController** — список/создание/редактирование панелей: `code`,
  `label`, `driver`, `isActive`, `supportedCurrencies` (JSON-редактор),
  write-only поле credentials. Список не показывает секреты.
- **DepositRequestCrudController** — список с фильтрами по статусу/панели/
  валюте/дате, детальная карточка со всей историей (когда создана, когда
  адрес выдан, когда увидены средства, история колбеков). Ручные действия:
  *"перепроверить сейчас"* (форс-тик поллера для одной заявки),
  *"отметить как expired/failed вручную"* (для явно зависших кейсов),
  *"переслать колбек"*.
- **WithdrawalRequestCrudController** — аналогично; ручной *"retry"*
  доступен только через тот же `clientWithdrawalId` (см. §5) — не создаёт
  новый вывод, а повторяет вызов с тем же идемпотентным ключом, чтобы не
  задвоить реальную отправку денег.
- **CallbackDeliveryCrudController** (или как вложенная вкладка в карточке
  заявки) — лог попыток доставки колбека, код ответа, ошибка, кнопка
  *"переслать сейчас"* для `exhausted`/`failed`.
- Один admin-firewall (`^/admin`, `ROLE_ADMIN`) — по тому же паттерну, что в
  Okean/rates-service.

## 8. Технологический стек

- PHP 8.5, Symfony 7.4, Doctrine ORM + doctrine-migrations, EasyAdmin —
  как в rates-service/Okean, для единообразия экосистемы.
- **symfony/http-client** для вызовов Binance REST API, с самописной HMAC-подписью
  запроса (Binance подписывает query string `HMAC SHA256` секретом —
  тривиально реализуется поверх `HttpClientInterface`), вместо стороннего
  `binance-connector-php`:
  - нужен полный контроль над сигнатурой запроса/обработкой ошибок,
    ретраями и логированием в едином стиле с `AbstractHttpPanel` — сторонняя
    обёртка это только усложнит;
  - обеспечивает единообразие с остальными проектами аккаунта, которые
    везде используют `symfony/http-client` напрямую (см. rates-service
    `composer.json`), а не exchange-specific SDK;
  - меньше поверхность для непредсказуемых breaking changes стороннего
    пакета вокруг чувствительной (withdrawal) функциональности.
- **symfony/messenger** (Doctrine transport для v1 — доп. брокер не нужен,
  легко переключить на Redis/AMQP позже без изменения кода дальше границы
  transport) — для асинхронной доставки колбеков с retry/backoff
  (`retry_strategy` с multiplier), вместо самописного retry-цикла.
- **symfony/lock** — не даёт двум копиям поллинг-воркера одной панели
  работать параллельно (на случай двойного старта systemd/деплоя).
- **symfony/uid** — uuid для id заявок и `event_id` колбеков.
- **ext-bcmath**, все денежные операции (сравнение `expectedAmount` с
  фактически зачисленным, суммы вывода) — только bcmath/строковое
  представление, никогда float — как в `LedgerService` Okean и
  `EffectiveRateCalculator` rates-service.
- Поллинг-воркеры — supervised systemd-сервисы (по образцу
  `rates-service-ingest@.service`), не cron/timer — интервалы измеряются
  секундами, что не подходит для периодического cron-запуска с полным
  bootstrap Symfony-контейнера на каждый тик.

## Риски и открытые вопросы (нужно решить с продукт-овнером до реализации)

**R1 — РЕШЕНО архитектурно (см. "Обновления по факту реализации" в начале
документа): пул `PanelWalletAddress` с холдом на заявку, вместо
уникализации суммы.** Остаётся открытым только операционный вопрос —
сколько реальных суб-аккаунтов Binance физически завести под пул.
Исходный текст риска ниже оставлен для контекста, почему это было риском:

Как отличить, какому депозиту принадлежит входящий платёж, если
Binance переиспользует один и тот же адрес.** Это главный риск всей схемы.
Повторный вызов "получить адрес депозита" для одной и той же пары
coin/network на Binance, как правило, возвращает **тот же самый адрес**, а
не новый уникальный. Значит, если у сервиса одновременно две активных
заявки на пополнение в USDT/TRC20 от разных пользователей — обеим может
быть выдан один и тот же адрес, и по факту поступления средств непонятно,
какой заявке их зачесть. Для большинства сетей (BTC, USDT-TRC20 и т.п.)
нет memo/tag, которым можно было бы разметить платёж, как это возможно для
XRP/EOS. Предлагаемый в этом документе `expectedAmount` как ключ
сопоставления — это компромисс (сопоставлять по сумме +
временному окну), а не гарантированное решение: если два пользователя
одновременно должны заплатить одинаковую сумму в одной валюте/сети, будет
коллизия. Возможные пути (окончательное решение — за продукт-овнером,
влияет на схему `DepositRequest` и на бизнес-процесс):
  - (a) искусственно уникализировать `expectedAmount`
    (добавлять на входе случайный "хвост" в младших разрядах, напр.
    150.00 → 150.000137, показывать пользователю именно эту сумму к оплате) —
    стандартный паттерн для платёжных шлюзов без нативной адресации, но
    требует, чтобы Okean показывал пользователю именно скорректированную
    сумму;
  - (b) один активный адрес = одна заявка одновременно на пару
    currency/network (сериализация выдачи), непрактично при заметном
    потоке;
  - (c) sub-аккаунты Binance (у каждого — свой адрес) — тяжелее в
    поддержке и завязано на лимиты Binance по числу саб-аккаунтов.
  Без выбора одного из этих подходов сервис в текущем виде **не может
  надёжно отличать заявки одной валюты/сети друг от друга**.

**R2 — Что происходит с `EXPIRED` заявкой, если деньги всё же пришли позже.**
Нужно решить: PG продолжает разово перепроверять expired-заявки ещё
какое-то время (и тогда шлёт "поздний" колбек) или считает деньги
потерянными для этой заявки/требующими ручного разбора в админке. Также не
определено, нужен ли Okean колбек на `deposit.expired` вообще, или это
чисто внутренний статус PG (Okean сам таймаутит заявку на своей стороне).

**R3 — Недоплата/переплата.** Если пришла не точная `expectedAmount`, а
меньше/больше — зачитывать частично, ждать донор, или сразу считать
ошибкой? Влияет на набор статусов (нужен ли `PARTIALLY_RECEIVED`) и на то,
что именно уходит в колбек. Сейчас не спроектировано намеренно — нет
входных данных для решения.

**R4 — Withdrawal address whitelisting на стороне Binance.** У биржевых
аккаунтов часто включена обязательная верификация нового адреса вывода
(email/2FA подтверждение), что блокирует полностью автоматический вызов
API до тех пор, пока адрес не белый список. Это операционный вопрос
(настройка аккаунта Binance), а не код, но архитектура withdrawal-флоу
предполагает, что вызов `executeWithdrawal` либо сразу успешен, либо сразу
известно, что зафейлился — если Binance вместо этого подвешивает вывод в
"pending manual approval", нужен третий промежуточный статус и его отдельно
не спроектировано.

**R5 — Callback URL статический или per-request.** Документ предполагает,
что у PG один статически сконфигурированный URL Okean-колбека на окружение
(из соображений безопасности — приём произвольного URL от вызывающей
стороны на каждый запрос создаёт SSRF-подобный вектор). Если у Okean
реально несколько окружений/instance, которым нужно по-разному
маршрутизировать колбеки — нужно явное подтверждение, что статической
конфигурации достаточно.

**R6 — Управление мастер-ключом шифрования credentials (§6).** Нужно знать,
есть ли уже в инфраструктуре аккаунта secret-manager (Vault/SSM/аналог)
или для v1 приемлем env-файл с ограниченными правами на хосте — от этого
зависит, нужен ли в архитектуре отдельный интеграционный слой сейчас или
можно отложить.

**R7 — Маппинг валют/сетей Okean ↔ Binance.** Предполагается, что Okean
передаёт `currency`/`network` уже в кодах, совместимых с тем, что ожидает
панель (Binance-совместимые тикеры и коды сетей). Если у Okean своя
внутренняя таксономия (напоминаю: `BlockchainNetworkDto` в Okean) —
может понадобиться таблица маппинга на стороне PG; в этой версии
архитектуры её нет, т.к. не было запрошено и не хотелось проектировать
впрок.

**R8 — Роутинг заявки на панель при нескольких активных панелях,
поддерживающих одну и ту же валюту.** Сейчас `Panel.supportedCurrencies`
описан как справочная информация, но алгоритм выбора "если валюту
поддерживают 2 активные панели — какую взять" не определён. Для v1
предполагается один активный панель на currency/network (проверяется при
создании заявки, при коллизии — ошибка конфигурации), полноценная
стратегия роутинга/fallback между панелями — сознательно не проектируется
сейчас, т.к. второй панели ещё нет и это была бы преждевременная
абстракция.

**R9 — Точные числовые параметры (интервалы поллинга, TTL адреса,
retry-расписание колбеков)** в этом документе — предложенные стартовые
значения, а не согласованные требования; их стоит явно подтвердить или
скорректировать перед реализацией, а не считать финальными.
